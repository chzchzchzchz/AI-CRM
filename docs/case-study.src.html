The problem

Storage isn't intelligence

A rep opens Salesforce and sees records. They open 6sense and see a score. Neither tells them which account to work this morning, or why. The judgement — the part that matters — happens in the rep's head, or not at all.

The obvious fix is to bolt an AI summary onto the CRM, and that is where most attempts quietly fail. Hand a model four thin fields and ask it for "intent signals, buying signals, competitive landscape" and it will produce all three, confidently, from nothing. The output reads like intelligence and is worth less than the raw record, because now it is also wrong.

I inherited exactly that: briefs that invented sections, and a second generation that over-corrected into bare facts scrubbed by roughly thirty regexes hunting hallucinations after the fact.

The approach

Split the work by what can be trusted

Facts and judgement are different jobs, so they are done by different things. A deterministic signal layer reads every stored data point and computes the numbers — intent trend from the time series, seniority inferred from titles, probability-weighted pipeline, open action items still outstanding from calls. No model touches them, so they are always true.

The model receives that finished pack and writes only the interpretation: the situation, why now, what to do, what could go wrong. Every item it returns must name the signal behind it. Categories with no data are reported as gaps rather than filled in.

Why it holds — fabrication becomes structurally impossible rather than filtered: the model never authors a name, a score, or a dollar figure. Those are rendered from the signal pack by code.

Engineering — what the audits found

Shipping meant proving it, not assuming it

A green build says the code compiles, not that the product works. Auditing the surface properly — 34 routers, 34 pages, roughly 250 procedures — turned up 65 places where the UI presented something as real that wasn't: columns read that don't exist in the schema, buttons wired to nothing, stubs returning empty arrays behind a working-looking panel.

The security pass mattered more. These were live in a repo about to be shown to people:

Critical

Password-reset codes returned in the API response

The endpoint generated a reset code, stored it, and handed it straight back to the caller while the mailer sat unused. Anyone could request a code for any address and read it. Now emailed; the response only echoes it in demo mode.

High

Brute-force lockout that never locked

The failure counter reset on every attempt, so the five-attempt threshold was unreachable — and the lockout was only enforced by middleware not mounted on the tRPC path. Fixed both; verified it locks and clears.

High

No prompt-injection boundary

Account descriptions from webhooks, call topics, uploaded CSVs and scraped search snippets were concatenated raw into prompts. Untrusted text is now fenced and labelled as data, with a trust boundary carried by the shared system prompts.

High

Salesforce sync erasing enriched data

The contact SOQL never selected LinkedIn, so every sync wrote null over URLs that enrichment had found. Now preserved when the source supplies nothing.

Verified — 307 tests passing · production build clean · pnpm audit reports no known vulnerabilities across the full tree, dev included.

Performance

Scale exposed the real bottleneck

Sixteen demo accounts hide everything. At a thousand accounts and ten thousand contacts, the contacts page was shipping the entire table to the browser on every load.

The fix bounds the default payload but runs search server-side across the full set, so no contact becomes unreachable. A related trap sat next to it: the AI prioritisation endpoint fed every contact into a single prompt, which at ten thousand rows would have been unusable — it now ranks by seniority and caps the set.
